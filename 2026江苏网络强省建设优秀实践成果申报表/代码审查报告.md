## 三、🔴 严重问题 (CRITICAL)

### 3.1 安全漏洞

#### 🔴 C-01: JWT 公钥由客户端提供 (`KeyCloakGranter.java:50-58`)

```java
// 用户传入的 JWT_SECRET_KEY 被直接用作 RSA 公钥来验证 JWT
algorithm = Algorithm.RSA256(
    stringToPublicKey(parameters.get("JWT_SECRET_KEY").toString().trim()),
    null
);
algorithm.verify(jwt);
```

**风险**: 攻击者可自签 JWT 并以任意用户身份登录。**可完全绕过认证。**

#### 🔴 C-02: 硬编码 RSA 私钥 (`RSATools.java:274, 294`)

```java
String privateKey = "MIICdwIBADANBgkqhkiG9w0BAQEFAASCAmEwggJdAgEAAoGBAJ0uSpu4+HfcT7r4vRP...";
```

**风险**: 生产环境 RSA 私钥硬编码在源码中，任何有仓库访问权限的人可签名伪造身份。

#### 🔴 C-03: SocialGranter 签名验证缺失 (`SocialGranter.java:47-78`)

`verifySignature()` 方法读取了 `sign` 参数但**从未验证其签名**。只需提供有效的时间戳即可伪造社交登录请求。

#### 🔴 C-04: `/oauth/check_token` 公开访问 (`AuthorizationServerConfig.java:104`)

```java
.checkTokenAccess("permitAll()")
```

无需认证即可验证任意 token 并提取用户信息，可被用于 token 枚举攻击。

#### 🔴 C-05: CSRF 全局禁用

`SecurityConfig.java:101`、`ResourceServerConfiguration.java:73`、`DefaultResourceServerConf.java:61` 三处均禁用 CSRF，且无 SameSite Cookie 等补偿措施。

#### 🔴 C-06: Token 允许 URL 查询参数传递 (`ResourceServerConfiguration.java:42`)

```java
tokenAuthenticationConverter.setAllowUriQueryParameter(true);
```

Token 出现在 URL 中会被服务器日志、浏览器历史记录、Referer 头泄露。

#### 🔴 C-07: 栈信息泄露 (`CustomAuthenticationEntryPoint.java:27`)

```java
authException.printStackTrace();
```

堆栈信息输出到 stderr，可能泄露内部路径、SQL 查询等敏感信息。

### 3.2 数据与业务逻辑漏洞

#### 🔴 C-08: SQL 注入 (`service-person/.../UserBaseMapper.xml:238-294`)

MyBatis XML 中使用 `${}` 字符串拼接，`fmt` 字段直接来自用户输入，可注入任意 SQL。

#### 🔴 C-09: BeanUtils.copyProperties 自拷贝 (`UserBaseServiceImpl.java:791,803`)

```java
BeanUtils.copyProperties(updateDTO, updateDTO);  // 拷贝到自己身上！
```

第二个参数应为 `userBase`，导致 `userBase` 对象始终为空，**新增/更新操作写入空数据**。

#### 🔴 C-10: 审计日志表结构与 INSERT 不匹配 (`DbAuditServiceImpl.java:28-60`)

`INSERT_SQL` 引用 17 列，但 `CREATE TABLE` 只定义了 10 列。缺少 `operation_type`、`area_code`、`channel`、`operation_model`、`url`、`type` 六列，且 `timestamp` 列名与 `create_time` 不匹配。**每次审计日志写入都会抛出 SQL 异常。**

#### 🔴 C-11: Redisson 分布式锁竞态条件 (`RedissonDistributedLock.java:57-61`)

```java
if (rLock.isLocked()) {
    rLock.unlock();  // TOCTOU 竞态：检查与操作之间锁可能被其他线程获取
}
```

`isLocked()` 检查与 `unlock()` 调用非原子操作，可能导致释放其他线程的锁。

#### 🔴 C-12: 自动填充逻辑错误 (`DateMetaObjectHandler.java:43-48`)

```java
if (createTime == null || updateTime == null || deleted == null || isDel == null) {
    // 任一字段为空就覆盖所有字段
}
```

使用 `||` 导致任一字段为空时所有字段都被覆盖。本意应是每个字段独立判断。

## 四、🟠 重要问题 (HIGH)

### 4.1 并发与线程安全

#### 🟠 H-01: ConcurrentModificationException (`AppBasePostServiceImpl.java:372-381`)

```java
listTwo.stream().forEach(one -> {
    list.stream().forEach(two -> {
        if (one.getAreaId().equals(two.getAreaId())) {
            listTwo.remove(one);  // 遍历时修改集合
        }
    });
});
```

遍历 `listTwo` 时调用 `remove()`，运行时抛出 `ConcurrentModificationException`。

#### 🟠 H-02: Flowable 递归中共享可变列表 (`FlowableUtils.java:258, 415`)

`iteratorFindDirtyRoads` 和 `findRoad` 方法中，`passRoads` 列表在递归分支间共享，导致分支间相互污染路径数据。

### 4.2 性能问题

#### 🟠 H-03 ~ H-08: N+1 查询问题（6 处）

| 文件 | 行号 | 问题 |
|------|------|------|
| `AppBasePostServiceImpl.java` | 85-111 | 每页记录循环中执行 4+ 次查询 |
| `AppBaseBuildingServiceImpl.java` | 66-72 | 循环中 2 次查询/记录 |
| `AppUserBaseServiceImpl.java` | 140-167 | 循环中 2 次查询/记录 |

**影响**: 每页 20 条记录时产生 60-80+ 次数据库查询，高并发下会严重拖垮数据库。

### 4.3 资源泄漏

#### 🟠 H-09: InputStream 未关闭 (`WfTaskController.java:151-176`)

`genProcessDiagram` 方法中 `inputStream` 在异常路径下未关闭，导致文件描述符泄漏。

### 4.4 异常处理

#### 🟠 H-10: Flowable 全局监听器静默吞异常 (`GlobalListener.java:87`)

```java

```

所有异常被静默吞噬，无日志、无监控，故障难以排查。

#### 🟠 H-11: 审计日志 NPE 风险 (`AuditLogAspect.java:119-133`)

- `RequestContextHolder.getRequestAttributes()` 在非请求上下文中返回 null
- `loginAppUser` 在未认证请求中为 null

### 4.5 其他

#### 🟠 H-12: 审计日志同步写入 (`DbAuditServiceImpl.java:86-88`)

`@Async` 被注释掉，每次审计日志写入阻塞请求线程，高并发下性能急剧下降。

## 七、架构与设计建议

### 7.1 安全架构

1. **统一认证加固**: 移除客户端提供的 JWT 公钥逻辑，使用服务端维护的受信任密钥
2. **签名验证**: SocialGranter 补全 RSA 签名验证
3. **CSRF 防护**: 启用 CSRF 或使用 SameSite Cookie + CORS 白名单
4. **Token 传递**: 仅通过 Authorization Header 传递 Bearer Token
5. **速率限制**: 在网关层对认证端点添加速率限制

### 7.2 数据层

1. **N+1 查询优化**: 所有循环内查询改为批量查询（`selectBatchIds`、`IN` 查询）
2. **SQL 注入修复**: 所有 `${}` 替换为 `#{}` 参数绑定
3. **审计日志修复**: 统一表结构与 INSERT 语句，启用异步写入

### 7.3 代码质量

1. **日志系统**: 全局替换 `System.out.println` / `e.printStackTrace()` 为 SLF4J
2. **BeanUtils 修复**: 修正 `copyProperties` 参数顺序
3. **并发修复**: 修复 `ConcurrentModificationException` 和 Redisson 锁竞态
4. **异常处理**: Flowable 监听器添加异常日志，审计日志添加空值保护

### 7.4 工程实践

1. **配置外部化**: 移除硬编码的 RSA 密钥、配置 ID、魔法数字
2. **统一框架版本**: kt-flowable 的 Spring Boot 2.7.6 与主项目 2.2.10 差异过大，建议对齐
3. **统一认证方案**: kt-flowable 使用 Sa-Token 而非主项目的 OAuth2，建议统一
4. **测试覆盖**: 项目缺少单元测试和集成测试

## 八、总结

该项目架构设计较为成熟，采用了微服务、OAuth2、Nacos、Sentinel 等主流技术，功能覆盖全面。但存在以下核心问题需要优先解决：

1. **🔴 安全漏洞严重**: 4 个严重安全漏洞（客户端提供 JWT 公钥、硬编码 RSA 私钥、签名验证缺失、check_token 公开访问）可导致系统被完全攻破
2. **🔴 数据一致性问题**: BeanUtils 自拷贝导致数据写入为空、审计日志写入必失败、分布式锁竞态条件
3. **🟠 性能瓶颈**: 6 处 N+1 查询、同步审计日志写入、Redis 批量操作非管道化
4. **🟠 并发缺陷**: ConcurrentModificationException、Flowable 递归共享可变列表

建议优先修复所有 CRITICAL 级别问题，其次解决 HIGH 级别的 N+1 查询和并发缺陷。
