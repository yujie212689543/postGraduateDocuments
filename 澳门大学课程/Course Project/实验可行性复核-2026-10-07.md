## 1. 关键事实核对：GPT-2 XL 到底要多少显存

来源：EasyEdit 官方 README「Editing GPU memory usage」表（默认配置）。

| 方法 | llama-2-7B | chatglm2 | gpt-j-6b | **gpt-xl** |
|---|---|---|---|---|
| FT | 60GB | 58GB | 55GB | **7GB** |
| SERAC | 42GB | 32GB | 31GB | **10GB** |
| IKE | 52GB | 38GB | 38GB | **10GB** |
| MEND | 46GB | 37GB | 37GB | **13GB** |
| KN | 42GB | 39GB | 40GB | **12GB** |
| **ROME** | 31GB | 29GB | 27GB | **10GB** |
| **MEMIT** | 33GB | 31GB | 31GB | **11GB** |
| AdaLoRA | 29GB | 24GB | 25GB | **8GB** |
| GRACE | 27GB | 23GB | — | **6GB** |
| WISE | 34GB | 27GB | — | **7GB** |

AlphaEdit 不在表中；它是在 MEMIT 式更新之上再做零空间投影，还要额外计算并保存协方差矩阵，所以峰值只会 ≥ MEMIT。

三条推论：

- **10–11GB > 8GB** → 5070 Laptop 8GB（Windows 实际可用约 7GB）**跑不动默认配置**。
- 更麻烦的是 README 明确写了：复现 ROME 在 KnowEdit 上的结果必须 **`fp16: False`**。也就是**不能用 fp16 省显存，只能 fp32**。fp32 下 GPT-2 XL 光权重就 6.2GB，再加激活、反向传播缓冲和 6400×6400 矩阵（每个 164MB，要好几份），到 10GB 是合理的。
- 这解释了看似矛盾的一点：模型本身只有 3GB（fp16），峰值却是 10GB。**"装得下模型"和"跑得完一次编辑"是两件事。**

**结论：编辑实验放 Kaggle T4（16GB）或 Colab T4。** 每周 30 小时 × 5 周 = 150 小时，够用。笔记本负责：读数据结构、写与调 runner 脚本（先用 gpt2 / gpt2-medium 这类小模型验证逻辑）、算指标、出图、写报告和 PPT。

> **补充（2026-10-07）**：组内另有一台 **12GB 显存**的 Windows 笔记本。12GB 下 ROME（10GB）**大概能跑通真实编辑**，MEMIT（11GB）悬、可能 OOM，AlphaEdit 基本不行。定位为**本地验证机**（跑通流程、单条编辑、小样本调试）；正式批量实验仍放 Kaggle T4，不要把交付赌在一台可能 OOM 的机器上。详见《减负方案-不影响成绩.md》第 3 节。

好消息：EasyEdit 主分支在 2026-07-08 做过大升级，支持 Transformers 5.x，安装也提供了 `uv pip install --torch-backend cu128`。之前担心的"50 系显卡装不上老版 PyTorch"风险已明显下降——但仍建议第一周就在 Kaggle 上把环境跑通，不要赌本机。

## 4. 到底有多"重"：把机器时间、人的时间、关键路径分开算

### 4.1 机器时间不是瓶颈

- ROME / MEMIT 是"改权重"的方法，不需要训练。EasyEdit 官方说法是每次编辑约 5 秒量级；T4 上保守估 20–60 秒。
- 100 次连续编辑 ≈ 0.5–1.5 小时 / 组。
- 组数：3 方法 × 2 数据集 × 3 顺序 = 18 组 → **约 9–27 小时 GPU 时间**。
- 再加 checkpoint 评测（1 / 10 / 100 三档，评测累计目标 + 改写 + locality + portability 探针），量级约几千次生成 / 组，18 组合计再几小时。
- 合计 **约 12–30 小时 T4**。Kaggle 每周 30 小时、5 周共 150 小时。**机器时间完全够，而且基本不用排队。**

### 4.2 人的时间：关键路径只有 30–40 人时

| 环节 | 人时（全组合计） | 集中在谁 |
|---|---|---|
| 环境 + 数据 + 跑通"一次编辑" | 15–25 | 1 人（最关键，也最容易卡） |
| 读 4 篇核心论文（略读级） | 12（3 人 × 4h） | 每人 |
| 写 runner、适配 KnowEdit 字段、顺序编辑状态管理 | 20–30 | 1–2 人 |
| Pilot + 指标校验 | 10–15 | 1–2 人 |
| 正式跑 + 盯盘（机器时间长，人的时间短） | 5 | 1 人 |
| 分析 + 出图 | 15–20 | 1–2 人 |
| 报告 / PPT / 视频 | 25–35 | 全组 |
| **合计** | **约 105–145 人时** | |

对照他的 140–210：他的下限比我的上限还高一点，差别主要在"环境摸索"和"写作"两块他给得更宽。

**真正的问题是分布，不是总量。** 上面 105–145 人时里，**只有 30–40 人时必须由会写代码的人承担**（环境 + runner + 状态管理 + 指标），其余都可并行：读论文、跑实验、出图、写报告、录视频。如果这三四十人时压在一个人身上、其他人干等，那就很难受；分工清楚的话，就是常规课程项目强度。

**换算成日常投入**：5 周、3 人，每人每周约 7–10 小时 ≈ 每天 1–1.5 小时。约为组员所写"每天 2–4 小时"的一半。

### 4.3 结论：在同类课程项目里算"中等偏轻"

- 不用训练大模型，不用自己设计算法，官方代码 + 官方配置 + 现成数据集。
- 真正难的只有两处：**第一次跑通**（一次性投入）和**顺序编辑的状态管理**（EasyEdit 的 `sequential_edit=True` 已覆盖主要场景）。
- 相比之下，"自己提新方法 + 训练 + 调参"的项目才重；而报告 v2 已把它定位成复现型，正好避开了那一档。

所以这不是"给自己找麻烦"，而是这门课里少见的、能被 8GB 笔记本 + 免费云算力包住的知识编辑课题。课程 Project 占 60%，要求复现 + 实验 + 报告 + 视频 + 展示，本来就轻不了；但在可选范围内，这个题已经在偏轻的一侧。

## 5. 建议的"安全通过"配置（时间比预期紧时按此砍）

从重到轻：

1. **数据集砍到一个**：只做 ZsRE。WikiData_counterfact 仅在时间富余时加。编辑组数 18 → 9。
2. **顺序砍到一条主线**：主实验只用 1 个固定顺序；另外 2 个顺序只对"最终方法 × 1 个数据集"做，用于支撑 RQ3。
3. **编辑数保留 100**：不建议砍，"连续编辑后遗忘"正是课题核心；砍到 50 也能讲，但故事会弱。
4. **AlphaEdit 放最后**：跑不起来就用 ROME + MEMIT + no-edit 收尾，报告如实写"AlphaEdit 因资源/兼容性未完成"。报告 5.5 节已为这种情况留了口子。
5. **portability 保底**：只报标注完整的子类，其余记 N/A（报告已写明该规则）。

**最小可信版本**：no-edit + ROME + MEMIT，1 个数据集，100 次连续编辑，1 条主顺序 + 1 条校验顺序，指标 = 编辑成功率 / locality / 旧编辑保留率。这套 5 周内一定能交。

## 7. 一句话回答"是不是给自己找麻烦"
