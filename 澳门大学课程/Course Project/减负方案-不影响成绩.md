# 项目减负方案：砍哪里、不砍哪里

**2026-10-07｜CISC7021 Course Project｜Group 36**

前提：目标是**通过并拿到体面的分数**。本文只列"减负但不掉分"的动作，说明每个动作对成绩的实际影响，以及需要用什么写法补回来。

---

## 0. 先看清分数花在哪里

按 Moodle 上的评分构成：

| 评分项 | 权重 |
|---|---|
| 课堂参与 | 5% |
| Review Report（Task 1） | 15% |
| 系统实现 | 20% |
| Final Report（Task 2） | 30% |
| 展示（Task 3 视频 + Task 4 课堂） | 30% |

三条推论：

1. **60% 的分数在"写"和"讲"上**。实验规模只通过"系统实现 20%"和"报告里的证据"间接影响分数，而那 20% 看的是"你有没有真的把方法跑起来"，不是"你跑了多少次"。
2. **一条讲透的对比，胜过四条跑不完的对比。** 减负的正确方向是减少"运行组数"，不是减少"讲清楚的问题数"。
3. Task 3 的 5 分钟视频是**同学互评**——观感、清晰度、demo 的直观程度，权重高于技术深度。这对我们是好消息：demo 便宜又好看。

还有一条隐性规则：老师和助教扣分通常扣在"方法理解错了""数字没有出处""结论吹过头"，很少扣在"实验只做了 100 次编辑"。

## 1. 减负清单（按"省多少 / 掉多少分"排序）

| # | 动作 | 省下的量 | 对成绩影响 | 怎么在报告里写才不掉分 |
|---|---|---|---|---|
| 1 | **数据集 2 → 1**（只做 ZsRE） | 运行量直接砍半 | 几乎没有 | 写"在 ZsRE 上的受控比较"，并在 limitation 里说明第二个数据集未纳入及原因。**不要写"我们验证了跨数据集泛化"** |
| 2 | **顺序 3 → 2**（1 条主顺序 + 1 条校验顺序） | 顺序实验省约 60% | 无损 | RQ3 改成"两条独立顺序的结果一致性检查"，比"顺序敏感性统计"更好讲也更诚实 |
| 3 | **不做任何超参消融**（层号 / rank / projection strength） | 省掉最大的一块 | 无损 | 报告 v2 的 5.5 节已明确划出范围，照写即可 |
| 4 | **基线收敛为 no-edit + ROME + MEMIT（+ AlphaEdit 若跑通）** | 省掉训练类基线 | 无损 | 写"训练类基线（MEND / SERAC / AdaLoRA）因算力限制不在范围内" |
| 5 | **AlphaEdit 排最后，允许如实写"未完成"** | 省 1–2 周 | 损失极小 | "AlphaEdit 因显存/兼容性未能在本协议下完成，保留为后续工作"。**诚实写不扣分，硬编数据才扣分** |
| 6 | **只取 3 个 checkpoint（1 / 10 / 100）**，不做"每次编辑后全量评测" | 评测开销降一个量级 | 无损 | 评测策略本就是设计选择，写清即可 |
| 7 | **下载官方预计算协方差统计**，不自己跑十万条 | 省几十分钟到 2 小时 | 无损 | 写明统计文件的来源与版本 |
| 8 | **每个 run 保存权重快照**，评测复用不重跑 | 省掉重复计算 | 无损 | 这正是报告 5.3 节要求的"run 之间状态正确恢复" |
| 9 | **Kaggle 双 T4 并行跑两组实验** | 墙钟时间砍半 | 无损 | 记入资源说明 |
| 10 | **本地先用 gpt2（124M）调通整条流水线**，再上 XL | 省掉大量"在 XL 上排错"的时间 | 无损 | 正常工程做法，报告不必写 |
| 11 | **prompt 模板与答案匹配规则第一周就冻结** | 省掉最容易反复的返工 | **反而加分** | "协议在正式评测前冻结"是 v2 报告已承诺的，做到就是加分项 |
| 12 | **Final Report 复用 Task 1 的文献与方法部分** | 省一整块写作时间 | 无损 | 正常做法，注意改时态（review → proposal → report） |
| 13 | **视频用录屏 demo + 每人一段旁白**，不做动画 | 省几十小时 | 无损 | 见第 5 节脚本 |

一句话：**上面 13 条全部执行，运行量能降到原方案的四分之一左右，而分数几乎不受影响。**

## 2. 唯一不能砍的东西

减负要保住"项目仍然成立"的底线，这三条不能动：

1. **旧编辑保留率（retention）**：整个课题的智力核心——"连续编辑后旧的会被忘掉"。
2. **locality（无关问题有没有被带坏）**：这是"知识编辑"区别于"直接微调"的关键指标。
3. **至少一个 unedited 基线**：没有它，所有数字都说不清是编辑带来的还是模型本来就有的。

砍实验规模可以；砍掉这三条，项目就从"研究"变成"跑脚本"了。报告 v2 已把这三条写进 RQ，保持即可。

## 3. 硬件更新：12GB 显存能承担到哪一步

组内有一台 12GB 显存的 Windows 笔记本，比 8GB 那台强不少，但边界要看清楚。

| 方法 | 官方默认配置 | 8GB 本 | **12GB 本** | Kaggle T4（16GB） |
|---|---|---|---|---|
| FT | 7GB | ⚠️ | ✅ | ✅ |
| ROME | 10GB | ❌ | ✅ 大概能跑（关掉浏览器等占用后可用约 11GB） | ✅ |
| MEMIT | 11GB | ❌ | ⚠️ 悬，可能 OOM | ✅ |
| MEND | 13GB | ❌ | ❌ | ✅ |
| AlphaEdit | ≥ MEMIT，可能 13GB+ | ❌ | ❌ 基本不行 | ⚠️ 需实测 |

结论与用法：

- **12GB 机器 = 本地验证机**：跑通流程、单条编辑、小样本、调试 runner。ROME 可以在上面跑真实编辑，这已经很有用。
- **正式批量实验仍放 Kaggle T4**：MEMIT 与 AlphaEdit 在 12GB 上不可靠，而 Kaggle 免费、16GB、每周 30 小时。**不要把交付赌在一台可能 OOM 的机器上。**
- 别忘了 `fp16: False` 这条硬要求——它意味着不能靠半精度把峰值压进 12GB。
- 若那台是 50 系显卡，第一周先验证 PyTorch/cu128 能否装通；40 系基本没这个坑。
- 顺手省事：跑之前关掉浏览器 / 视频 / 微信，Windows 会吃掉约 1GB 显存；实验切成一两小时一段，避免长时间降频。

## 4. 人力减负：关键路径只有 30–40 人时

| 环节 | 人时 | 建议归属 |
|---|---|---|
| 环境 + 数据 + 跑通一次编辑 | 15–25 | A（技术） |
| 读 4 篇核心论文（略读） | 12 | 每人 4h |
| runner / KnowEdit 字段适配 / 顺序状态管理 | 20–30 | A |
| Pilot + 指标校验 | 10–15 | A + B |
| 正式跑 + 盯盘 | 5 | A |
| 分析 + 出图 | 15–20 | B + C |
| 报告 / PPT / 视频 | 25–35 | 全组 |
| **合计** | **约 105–145 人时** | |

三人分工建议：

- **A = 实现与运行**：环境、runner、状态管理、跑实验。**关键路径都在他身上，所以其他人的任务是"不要让他等人"。**
- **B = 数据与评测**：数据清单、标注覆盖率核查、指标口径核对、结果抽查。**不需要会写训练代码，但要会看数。**
- **C = 分析与写作**：图表、报告、PPT、视频剪辑。**这是 60% 分数的直接来源，不要把它当"打杂"。**

减负要点：**三人共用一套流程与一份配置**，不要各写一套——那是最容易产生隐性工时的地方（三份脚本 → 三倍调试 → 结果无法比较）。

投入换算：5 周、3 人、每人每周约 7–10 小时 ≈ **每天 1–1.5 小时**，比"每天 2–4 小时"的规划值低一半。

## 5. 几乎零成本、但直接加分的动作

这些不算减负，是"用更少的力气换更多分"，性价比最高：

1. **30 秒 demo 录屏讲完主线**：提问 → 模型答错 → 编辑 → 答对 → 问一个无关问题 → 没被带坏。这一条同时喂饱 Task 3 视频和 Task 4 展示。
2. **一张"编辑数 vs 保留率"折线图当主结果**：三条线（ROME / MEMIT / AlphaEdit）+ 一条 no-edit 参考线。图比表好看，也比表好讲。
3. **诚实写失败案例**：AlphaEdit 跑不动、某方法 OOM、某类 portability 标注缺失——写出来是加分项，藏起来被问到是减分项。
4. **复现包**：config + 随机种子 + 代码 commit 号 + run log。一句"我们记录了完整复现信息"，评审印象分很高，成本几乎为零。
5. **背一句标准回答**：被问"你这不就是 AlphaEdit 的零空间投影吗"——答："我们的定位是复现与受控比较，不主张新的投影方法（报告 5.5 节已写明）。"
6. **每个数字标出处**：版本号（arXiv:2410.02355v3 / 2401.01286v5）、表号、是文献值还是本次实测。最容易被追问，也最容易做对。
7. **展示结构（4 分钟）**：30s 问题 / 60s 方法 / 90s 结果图 / 30s 失败与限制 / 30s 结论。约 7 页，别塞满字。
8. **视频（5 分钟）**：前 30 秒放 demo 录屏，中段每人讲自己负责的一块，最后 30 秒讲限制与下一步。全员出镜是硬要求，别漏。

## 6. 减负版最小可行方案（一页纸）

| 项目 | 内容 |
|---|---|
| 模型 | GPT-2 XL（1.5B），EasyEdit 官方配置 |
| 方法 | no-edit（基线）+ ROME + MEMIT；AlphaEdit 视资源追加 |
| 数据集 | ZsRE（主）；WikiData_counterfact 仅在时间富余时加 |
| 编辑规模 | 每条序列 100 次连续编辑，checkpoint 取 1 / 10 / 100 |
| 顺序 | 1 条主顺序；1 条校验顺序（只对主方法与主数据集） |
| 指标 | 编辑成功率、locality、旧编辑保留率（必做）；portability 只在有标注子集上报，缺失记 N/A |
| 算力 | 正式跑放 Kaggle T4（免费，30h/周）；12GB 本机做验证与单条编辑调试 |
| 运行组数 | **约 6–9 组**（原方案 18 组） |
| 预计 GPU 时间 | 约 5–12 小时 T4 |
| 结论口径 | "在 ZsRE 上、GPT-2 XL 下，按固定协议复现并比较三种方法；不主张新算法" |

## 8. 一句话总结

分数的大头在报告与展示（60%），不在编辑次数。所以减负的正确做法是：**把运行组数从 18 组砍到 6–9 组，把省下来的时间全部投到"一张好图 + 一段好 demo + 诚实的限制说明"上。** 这样做，工作量约为原方案的四分之一，而分数基本不动。
