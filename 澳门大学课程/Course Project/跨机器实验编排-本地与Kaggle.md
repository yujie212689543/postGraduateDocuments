# 跨机器实验编排：本地与 Kaggle 怎么分工才不乱

**2026-10-07｜CISC7021 Course Project｜Group 36**

回答两个具体担心：
1. 本地跑了一部分，Kaggle 上跑剩下的，Kaggle 会不会因为没有前面的结果而跑不起来？本地数据要不要在 Kaggle 重跑？
2. 两地环境不同，来回切换会不会越弄越乱？

---

## 0. 一句话原则

**不要让"上一次运行的内存状态"成为下一步的输入。**

**run 是实验的最小单位，必须能在任意一台机器上独立跑完整。**
做到这一条，"接力"和"环境漂移"这两个问题就都不存在了。

---

## 1. 先分清三类东西（混在一起才会乱）

| 类别 | 例子 | 怎么保证两边一致 |
|---|---|---|
| **代码** | runner、指标函数、prompt 模板 | 只在一处修改；用 git commit 号标识每一版 |
| **数据** | ZsRE 的 100 条样本 | 一开始生成 `manifest.json`（样本 ID 列表），两边都用它 |
| **产物** | 指标 JSON、日志、权重快照 | 都是文件，可下载/上传；小文件（JSON）随便传 |

---

## 2. 回答担心一：Kaggle 不需要本地的中间结果

关键在于"连续编辑"是怎么实现的：

- 一次连续编辑的 100 条，**中间状态（权重、方法内部状态）在内存里**。所以：
  - **一个 run 必须在一台机器上跑完。中途换机器 = 那个 run 作废重跑。**
  - 技术上也能接力（到第 50 条时把权重 + RNG state + AlphaEdit 的协方差/投影缓存一起存盘，上传到 Kaggle 继续），但**很脆**：任何一个内部状态漏存，结果会静默出错，而且不容易发现。**不建议。**
- 如果本地只跑了"前 50 条"，Kaggle 想接着跑，就必须拿到本地上一步的权重快照（GPT-2 XL 约 3–6GB）——上传麻烦、还容易出错。

**所以正确做法不是接力，而是分工：**

> **每个 run = (模型, 方法, 数据集, 顺序, 编辑条数)，从原始 checkpoint 开始，在一台机器上跑完，输出结果文件。**

本地跑不完的，**不要跑一半再搬**，直接在 Kaggle 上重跑整个 run。

本地那些小实验（gpt2 124M 上验证流程、10 条样本的冒烟测试）**只当流程验证，不进正式结果表**——所以也不需要和 Kaggle 的结果拼在一起。

---

## 3. 回答担心二：环境不会乱，只要"只在一个地方改代码"

乱的真正原因通常不是环境，而是这三件事同时发生：**两边都改代码、两边都随手装包、两边都当主力跑。**

三条纪律：

1. **只在一处修改代码**（推荐：本地写，Kaggle 跑）。
   - 同步方式：私有 GitHub 仓库，或 Kaggle 上 `%%writefile run.py` / 上传脚本。
   - 每次同步记录 commit 号，写进结果 JSON。
2. **每台机器每次会话都从同一个 `requirements.txt` 装起**，不要依赖"上次装过"。
   - Kaggle notebook 每次会话环境会重置，所以开头固定一个 cell：`!pip install -r requirements.txt`（需打开 Internet 开关）。
   - 版本号要锁死（EasyEdit 对 transformers 版本敏感）。把关键包版本打印出来存进 run 日志，两边对得上才算环境一致。
3. **固定随机种子**：`torch.manual_seed` / numpy seed 两边一致，否则结果不可比。

**最常见的"环境不同"其实不是环境，是路径。** 代码里所有路径都用相对路径或环境变量，不要写 `C:\Users\...` 或 `/Users/gu/...`。

---

## 4. 推荐的两种编排（选一种，别混）

**方案 A（推荐）：Kaggle 当主力，本地只做轻活**

| 机器 | 干什么 |
|---|---|
| 本地（8GB / 12GB） | 读论文、看数据、写与调代码、gpt2 小模型跑通流程、画图、写报告 |
| Kaggle T4（16GB） | 所有 GPT-2 XL 的正式 run |

优点：根本不存在"接力"问题。本地跑的全是流程验证，不需要和正式结果拼。

**方案 B：本机 12GB 跑 ROME 的 run，Kaggle 跑 MEMIT / AlphaEdit 的 run**

可行，前提是每个 run 独立完整、两边共用同一份代码/数据/指标。跑完把两边的结果 JSON 下载到本地合并成一张表。

**不要**：本地跑一半 → 传权重到 Kaggle 接着跑。

---

## 5. 操作要点（照做即可）

1. **每个 run 结束落盘一个 `metrics.json`**，字段至少包含：
   - `config`（模型、方法、数据集、顺序、编辑数）
   - `git_commit`、`requirements_versions`
   - `dataset_manifest_id`（或样本 ID 列表的哈希）
   - `seed`
   - 指标（编辑成功率、locality、retention…）
   - `peak_gpu_mem`、`wall_time`、`device`
2. **数据先冻结再跑**：第一周生成 `manifest.json`，两边都用它，保证"本地跑的和 Kaggle 跑的是同一批样本"。
3. **Kaggle 的结果要保存**：写完 `/kaggle/working` 后点 **Save Version**，否则会话结束就没了。数据可上传为 Kaggle Dataset 挂载。
4. **一次会话跑得完**：Kaggle notebook 单次约 9–12 小时上限。ROME 100 条约 0.5–1.5 小时，没问题；不要在一个 session 里塞 5 个 run。
5. **跨机器的结论只做"趋势对照"**：如果 ROME 在 12GB 本机跑、MEMIT 在 Kaggle 跑，报告里要注明设备差异；不要把它们当成完全同条件的对比。

---

## 6. 验收标准（自检用）

> **任意一台机器，给我 commit 号 + requirements + manifest，我就能把整个实验重跑出来。**

做到这一条，就不存在"Kaggle 缺前面的结果""环境来回装"这类问题。做不到，说明某个 run 还依赖了机器上的临时状态——那才是真正会返工的地方。

---

## 7. 直接回答你的两个问题

- **"Kaggle 会不会因为没有本地前面的结果而跑不起来？"**
  不会——只要你别去"接力"。每个 run 独立跑完整。本地跑一半的 run 直接在 Kaggle 重跑，比传权重过去更省事、更不容易错。
- **"环境不同会不会来回装、最后都乱了？"**
  会乱的原因不是"环境不同"，而是"两边都改、都装、都当主力"。**只在一处改代码（本地写、Kaggle 跑）+ 每次会话从同一个 requirements 装起 + 每个 run 独立可重跑**，就不会乱。
